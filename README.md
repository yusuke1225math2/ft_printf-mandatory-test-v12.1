# ft_printf テスト

`libftprintf.a` (mandatory パートのみ) のテスト集です。
テストは採点対象ではありません。提出前と評価中にライブラリを確認するために使います。
`tests/test_all.sh` を 1 回実行すると、次の順番でまとめて確認できます。

1. `norminette` (`*.c` と `*.h`)
2. `make` の各ルールと relink の確認
3. テストプログラムのビルド
4. write 失敗、同一プロセス比較、未定義動作のテスト (ASan + UBSan 付き)
5. `valgrind` によるメモリエラーとリークの確認
6. 本物の `printf` と `ft_printf` の出力の `diff`

測定環境は Ubuntu 24.04、gcc 13.3、glibc 2.39、x86_64 です。下の表の「出力」と
「ret」は、このマシンで本物の `printf` が出した値です。`ft_printf` もすべて同じ結果でした。

## 利用時の注意

- **カバー範囲は mandatory のみです。** Bonus (フラグや幅など) はテストしていません。
  このテストに合格しても、Bonus の動作は確認できていません。
- **実装によっては一部のテストがうまく動かない可能性があります。** このテストは作者の実装に合わせて
  書かれています。`KO` やエラーが出ても、実装のバグとは限りません。テストの狙いを読んで判断し、
  必要なら自分の実装に合わせてテストを調整してください。たとえば次のような場合です。
  - 未定義動作のテスト (`trailing %`、`unknown spec`、`NULL fmt`) は、glibc に合わせた挙動を期待しています。
    別の挙動を選んだ実装では `KO` になります。`NULL` の書式で落ちる実装では、そこでスクリプトが止まります。
  - write 失敗のテストは、`write` が失敗したら以後の書き込みをやめて `-1` を返すことを期待しています。
  - ソースやヘッダをサブフォルダに置く構成では、`norminette *.c *.h` や
    `#include "../ft_printf.h"` が失敗します。
- **macOS では、期待値のズレが原因で `KO` や差分が出る場合があります。** 期待値は Linux の glibc を
  基準にしているので、実装のバグとは限りません。
- **レビューでは中身を説明できるようにしてください。** レビュー時にこのテストコードを使用したことを
  述べる場合や、レビュー時にこのテストコードで動作確認をする場合は、
  各テストが何をどのように確認しているのかを説明できるようにしておいてください。
  テストの内容は[テストの種類](#テストの種類全-105-件)以降で説明しています。

## 必要なもの

| ツール | 用途 |
| --- | --- |
| `cc` | テストのビルド |
| `make` | `libftprintf.a` のビルド |
| `norminette` | Norm チェック |
| `valgrind` | メモリエラーとリークの確認 (`test_all.sh` の必須ステップ) |

比較の基準は glibc なので、Linux での実行を想定しています。

**macOS の場合の注意**: macOS では `valgrind` が使えません。そのまま実行すると、valgrind の
ステップで `command not found` になってスクリプトが止まり、最後の `diff` まで進みません。
`test_all.sh` の valgrind の行をコメントアウトしてから実行してください
(手順は[一部のステップだけ実行する](#一部のステップだけ実行する)を参照)。
また、`diff` では `SP_00` と `p_05` に差が出ます ([既知の限界](#既知の限界)を参照)。

## 設置方法

このテスト集は公開リポジトリ
[yusuke1225math2/ft_printf-mandatory-test-v12.1](https://github.com/yusuke1225math2/ft_printf-mandatory-test-v12.1)
で配布しています。自分の ft_printf フォルダ (以下 `your_ft_printf/`) の直下で、`tests` という名前を付けて
`git clone` します。

```bash
cd ~/your_ft_printf
git clone https://github.com/yusuke1225math2/ft_printf-mandatory-test-v12.1.git tests
```

最後の `tests` は clone 先のフォルダ名です。省略すると
`ft_printf-mandatory-test-v12.1/` という名前になり、テストが動かないので必ず付けてください。

設置後は次のような構成になります。

```text
your_ft_printf/
├── Makefile
├── ft_printf.h
├── *.c
└── tests/
    ├── README.md
    ├── test_all.sh
    ├── test_cases.h
    ├── test_ft_printf.h
    ├── out_printf.c
    ├── out_ft_printf.c
    └── test_write_fail.c
```

注意点:

- `your_ft_printf/` が Git リポジトリの場合、`tests/` は別リポジトリなので
  提出物に含めないでください。`your_ft_printf/.gitignore` に `tests/` と `tmp/` を追加しておくと
  誤って `git add` するのを防げます (`tmp/` は実行時に作られます)。
- `test_ft_printf.h` は `#include "../ft_printf.h"` で自分のヘッダを読み込むため、
  必ず `your_ft_printf/tests/` という位置に置いてください。
- `Makefile` が `libftprintf.a` を作り、`clean`、`fclean`、`re` のルールを持っている必要があります。
- スクリプト中のコマンドは `tests/` や `libftprintf.a` を相対パスで参照するので、
  実行は必ず `your_ft_printf/` 直下から行います。

## 実行方法

### 1. `your_ft_printf/` 直下に移動する

```bash
cd ~/your_ft_printf
```

### 2. 実行する

```bash
bash tests/test_all.sh
```

出力をファイルに残したいときは、次のようにします。

```bash
bash tests/test_all.sh 2>&1 | tee test.log
```

スクリプトは最初に失敗したステップで止まります (`set -euo pipefail`)。

| ステップ | 内容 | 合格条件 |
| --- | --- | --- |
| norminette | `norminette *.c *.h` | すべてのファイルが `OK!` |
| make | `fclean`、`make`、`make`、`re`、`clean`、`make` | ビルドできる。2回目の `make` が `Nothing to be done` と表示する (relink しない) |
| ビルド | `tmp/a.out` (本物の `printf`)、`tmp/b.out` (`ft_printf`)、`tmp/c.out` (ASan + UBSan) | コンパイルできる |
| `tmp/c.out` | write 失敗、同一プロセス比較、UB のテスト | stderr に `ALL OK (0 KO)` |
| valgrind | `valgrind --error-exitcode=1 --leak-check=full tmp/b.out` | メモリエラーもリークもない (あれば終了コード 1 でスクリプトが止まる) |
| diff | `diff -a tmp/a.log tmp/b.log` | 何も出力されない |

## 結果の見方

`tmp/c.out` は、ケースごとに `OK` / `KO` を表示し、最後にまとめを出します。

```text
OK: fail plain
OK: fail c
...
ALL OK (0 KO)
```

- `KO: <名前>` が出たら、そのケースが失敗しています。
- 失敗があると最後に `KO (N KO)` と表示され、終了コード 1 でスクリプトが止まります。
- AddressSanitizer や UndefinedBehaviorSanitizer がエラーを見つけると、そのレポートが表示されます。
- valgrind がメモリエラーやリークを見つけると、そのレポートが表示され、スクリプトが止まります。
- 最後の `diff` は、何も出力されなければ合格です。差があると、`<` の行に本物の `printf` の結果、
  `>` の行に `ft_printf` の結果が表示されます。

## 一部のステップだけ実行する

`tests/test_all.sh` を開き、不要なステップの行を `#` でコメントアウトしてから、
いつもと同じように実行します。次の例は norminette と valgrind を飛ばします。

```sh

```

```sh

```

テストのリンクに `libftprintf.a` が必要なので、`make` の行は残してください。
テストプログラムをビルドする `cc` の行と `mkdir -p tmp` も残します。

## 1. `printf` との比較（84 件）

### 仕組み

- 各ケースは `test_cases.h` に 1 回だけ書いています。`out_printf.c` と
  `out_ft_printf.c` が同じマクロを使うので、両方が必ず同じケースを実行します。
- ケースごとに、ラベル・出力・戻り値を表示します。
  例: `CASE_d_00   : 0` のあとに `CASE_d_00   (ret): 1`
- `#__VA_ARGS__` で引数をラベルの文字列にしています。`#` 演算子はマクロを展開しないので、
  ラベルは中身ではなくケース名（`CASE_d_00`）になります。
- マクロは `do { ... } while (0)` で囲んでいるので、1 つの文として扱えます。
- 各呼び出しの前後で `fflush(stdout)` を呼んでいます。`printf` はバッファリングされ、
  `ft_printf` は直接 `write` するので、flush しないとラベルと出力の順番が入れ替わることがあります。
- `diff -a` でテキストとして比較させています。NUL バイトやバイト 200 を出すケースがあるので、
  `-a` がないと diff は「binary files differ」としか言いません。
- `out_printf.c` は `-Wall -Werror` なしでビルドしています。`printf("%s", NULL)` や
  `printf("abc", 42)`（SP_09）などに gcc が警告（`-Wformat`）を出すためです。`ft_printf` には format 属性がないので、
  `out_ft_printf.c` はフラグ付きでビルドできます。
- ここで比べるポインタは固定値だけです。スタックやヒープのアドレスは実行のたびに変わる（ASLR）ので、
  3 で比べています。

下の表の `␀` は NUL バイト 1 つを表します。

| PER_02 | `"100%%"` | `100%` | 4 | 書式の末尾に `%%` |
| PER_03 | `"%%d"` | `%d` | 2 | `%%` のあとの `d` は普通の文字で、引数を取らない |
| PER_04 | `"%%%c", 'x'` | `%x` | 2 | `%%` の直後に変換 |
| PER_05 | `"%d%%", 50` | `50%` | 3 | 変換の直後に `%%` |

## 2. write 失敗（14 件、`TEST_FAIL_EACH`）

### 仕組み

- `test_write_fail.c` は自分で `write` を定義しています。`libftprintf.a` は静的ライブラリなので、
  リンカは `ft_putchar.o` の `write` 呼び出しを libc ではなくこの定義に結びつけます。
  `fprintf(stderr, ...)` は影響を受けません（glibc は内部で公開シンボルの `write` を経由しない）。
  そのため、結果は stderr にそのまま表示されます。
- 各ケースで次のことをします。
  1. 1 回普通に実行して、`write` の呼び出し回数 N を数える。
  2. 1 回目、2 回目、…、N 回目の呼び出しを順に失敗させる（`k_` = 1〜N）。これを 2 通り行う。
     `write` が `-1` を返す場合と、`0` を返す場合（`r_` = -1、0）。
  3. 毎回、戻り値が `-1` であること、失敗のあとに `write` を一度も呼ばないことを確かめる。
     後者は `g_calls != k_` で判定しています。k 回目で失敗させたのに `write` の呼び出し回数が
     k より多ければ、失敗のあとも書き続けたということです。
- `0` もエラーにする理由: `ft_putchar` は 1 バイト書いて `!= 1` で判定しています。
  `0` のあとにリトライすると、無限ループになるおそれがあります。
- 部分書き込みが問題にならない理由: 1 回に 1 バイトしか書かないので、結果は「書けた」か
  「書けなかった」の 2 通りしかありません。
- 大事な理由: `printf` は出力エラーのとき負の値を返します（C11 7.21.6.1p14、`printf(3)`）。
  このバグは 1 の `diff` では見つかりません。`write` が成功すれば出力は正しいからです。

### ケース

| 名前 | 入力 | write 回数（N） | 確かめる経路 |
| --- | --- | --- | --- |
| fail plain | `"abc"` | 3 | 普通の文字（`ft_printf` の `else` 側） |
| fail c | `"%c", 'a'` | 1 | `ft_putchar` 単体 |
| fail c NUL | `"[%c]", '\0'` | 3 | NUL を書くときに失敗しても `-1` を返す |
| fail s | `"x%sy", "hello"` | 7 | `ft_putstr` のループの途中で失敗 |
| fail s NULL | `"%s", NULL` | 6 | `"(null)"` の経路 |
| fail p | `"%p", &local` | 14 | `"0x"` の部分と、`ft_putaddr` の再帰のすべての深さ |
| fail p NULL | `"%p", NULL` | 5 | `"(nil)"` の経路 |
| fail d | `"%d", INT_MAX` | 10 | 10 段の再帰のすべての深さ |
| fail d INT_MIN | `"%d", INT_MIN` | 11 | `'-'` を書くところでの失敗も含む |
| fail u | `"%u", UINT_MAX` | 10 | `ft_putunsigned` の再帰 |
| fail x | `"%x", 0xdeadbeef` | 8 | `ft_puthex` の再帰 |
| fail %% | `"a%%b"` | 3 | `%%` の経路 |
| fail mixed | `"%s=%d%c", "n", 12, '\n'` | 5 | エラーが別々のヘルパー関数をまたいで伝わる |
| fail unknown | `"a%yb"` | 4 | 不明な指定子の経路（`ft_putchar` を 2 回呼ぶ） |

## 3. 同一プロセス比較（4 件、`TEST_SAME`）

期待する結果は、同じプロセスの中で `snprintf` に作らせます（glibc の `printf` と同じ整形処理を使う）。
出力のバイトと戻り値の両方を比べます。

| 名前 | 入力 | 狙い |
| --- | --- | --- |
| p local | `"%p", &local` | スタックのアドレス。実行ごとに変わる（ASLR）ので、2 つのプログラムでは比べられない |
| p static | `"%p", &global` | static 変数。PIE でビルドするとこれも実行ごとに変わる |
| p heap | `"%p", malloc(1)` | ヒープのアドレス（テスト側で free している） |
| s 20000 in [] | 20000 個の `x` を `"[%s]"` で | 長さに上限がない（固定長のバッファを使っていない）。長い出力のあとの文字も出る |

## 4. 未定義動作（3 件、`TEST_EXPECT`）

C 規格はこれらの呼び出しの結果を定めていません。
`ft_printf` は、このマシンで測った glibc 2.39 の挙動に合わせています。

| 名前 | 入力 | 期待する出力 | ret | 理由 |
| --- | --- | --- | --- | --- |
| trailing % | `"abc%"` | `abc` | -1 | glibc も `abc` を出して `-1` を返す |
| unknown spec | `"a%yb"` | `a%yb` | 4 | glibc も `%y` をそのまま出す |
| NULL fmt | `NULL` | （なし） | -1 | glibc も `-1` を返し、`errno` に `EINVAL` を設定する |

フラグと幅（`"%5d"`）はボーナスの機能です。`ft_printf` は `%5` を不明な指定子として扱い、
落ちずに `%5d` を出力します（ret 3）。

## 既知の限界

- relink の確認は目視です。2 回目の `make` が `Nothing to be done for 'all'` と表示することを確かめます。
- 比較の基準は glibc です。macOS では `%p` に `NULL` を渡すと `0x0` が出るので、
  `SP_00` と `p_05` は一致しません。
